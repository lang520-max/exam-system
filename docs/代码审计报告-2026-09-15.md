## 严重（直接影响考试公平性 / 鉴权）

### 1. 交卷不校验考试时限 —— 倒计时纯属装饰【实测】

**证明过程**：seed 数据里考试 2 时长 45 分钟。我以 student02 开考（recordId=2），
直接把 H2 里的 `start_time` 回拨 3 小时，再交卷：

```
start_time = 2026-09-15 20:19:04
end_time   = 2026-09-15 23:19:14      ← 实际历时 3 小时
POST /api/exams/submit  ->  HTTP/1.1 200
{"code":200,"data":{"status":"PENDING_GRADE","message":"提交成功..."}}
最终库中状态: score=20, status=2 (已出分)
```

服务端**没有拒绝、没有标记超时**，照常判分。服务端自己算出的截止时刻显示"已超时 135 分钟"，
但记录状态仍是 `0 考试中`。

**根因**【读码，逐行读过 `ExamService.submitExam` 全文 144-221 行】：
该方法做了：幂等校验 → 记录存在性 → 归属校验 → `status == ONGOING` 校验 → CAS 抢占 → 存答案 → 判分。
**全文没有任何一处比较时间**（无 `deadline`、无 `duration`、无 `startTime` 比较）。

**并且**：全项目搜索 `@Scheduled` / `@EnableScheduling` **零命中**——没有任何定时任务。
`RecordStatus.TIMEOUT = 3` 在常量类里定义了、`statusText` 里也做了中文映射，
但**没有任何代码路径会把它写进数据库**——是个死常量。
唯一的 TIMEOUT 是 WebSocket 推给前端的一条消息。

**后果**：
- 学生开考后挂机任意久都能交卷，服务端照常判分 → 考试时间限制形同虚设
- 学生只要永不交卷，记录永远卡在"考试中"，没有清理机制
- `ExamWebSocketHandler` 注释里"Redis TTL 作为倒计时真相（单源）"只在**显示层**成立，不构成任何约束

**修法**：`submitExam` 中计算 `deadline = record.startTime + exam.duration`，
超时则拒绝（或标记 `TIMEOUT` 后仍判分，按教学需求定）；另加 `@Scheduled` 扫描清理过期 ONGOING 记录。

### 2. WebSocket 不校验 token 是否归属于路径里的 userId —— 可踢掉任意考生【读码】

`ExamWebSocketHandler.onOpen`（63-83 行）：
```java
String token = getTokenFromSession(session);
if (token == null || jwtUtil == null || !jwtUtil.validate(token)) { closeSession(...); return; }
String sessionKey = examId + ":" + userId;      // ← userId 来自 URL 路径参数
Session oldSession = SESSION_MAP.get(sessionKey);
if (oldSession != null && oldSession.isOpen()) {
    closeSession(oldSession, "新设备登录");       // ← 互踢
}
```

端点：`@ServerEndpoint("/ws/exam/{examId}/{userId}")`

**它只验证"这是个合法 JWT"，从不比较 `jwtUtil.getUserId(token)` 与路径参数 `userId`。**
而 `SecurityConfig` 里 `/ws/**` 是 `permitAll`，鉴权**完全**依赖这一段。

**后果**：任何已登录学生，用**别人的 userId** 连接 `/ws/exam/1/5`，就会触发"互踢"逻辑，
**把对方正在考试的 WebSocket 连接关闭**。反复重连即可在考试过程中持续干扰同学，
对方会丢失倒计时推送与自动交卷通知。同时攻击者能收到对方的倒计时数据流。

**修法**：`onOpen` 里加一行断言——`jwtUtil.getUserId(token)` 必须等于路径 `userId`，否则关闭连接。
（未做运行时验证：需要一个 WebSocket 客户端，属额外工具链；代码路径明确，不存在其他校验分支。）

### 3. Refresh Token 与 Access Token 不可区分 —— 短命 token 可换出 7 天 token【实测】

`JwtUtil.generateToken`（43-53 行）对两种 token 使用**完全相同的 claims**
（subject / username / role），只有 `expire` 不同，**没有 `typ` 类型声明**。

`AuthService.refresh`（92-99 行）只调 `getUserId` / `getUsername` / `getRole`，**不校验 token 类型**。

**证明过程**：以 student01 登录拿到 30 分钟的 access token，直接拿它调 refresh 接口：
```
POST /api/auth/refresh   X-Refresh-Token: <access token>
-> HTTP/1.1 200  且响应体含 "accessToken"（发回了全新 token 对）
```

**后果**：双 Token 方案的核心目的（用短命 access token 限制泄露窗口）被完全绕过。
一旦 access token 泄露，攻击者可自行续签出 7 天的 refresh token；且服务端无法吊销。

**修法**：`generateToken` 增加 `typ` claim（"access"/"refresh"），`refresh()` 里校验必须为 "refresh"。
进一步可做 refresh token 轮换 + 白名单（Redis）。

## 中等

### 4. 学生能拿到未发布试卷的完整题目快照与组卷规则【实测】

```
GET /api/exams/1        (以学生 token)  -> 200
返回字段: id, title, ..., ruleConfig, questionSnapshot, ...
questionSnapshot = [{"questionId":1,"score":10},{"questionId":2,"score":10},...]   ← 卷子上是哪几题、各多少分
ruleConfig       = {"rules":[{"type":0,"count":2,"score":10},...]}                  ← 组卷规则
```

`ExamController.getExam`(71) 直接返回 `Exam` **实体**，未做字段裁剪；
`listExams`(55) **没有任何状态过滤**，还显式接受 `?status=0`（草稿）。

配合 `/api/auth/register` 公开注册（**角色被硬编码为 2 学生，不能提权——这点是对的**），
**任何人注册个学生号就能提前拿到未发布卷子的构成**。

**修法**：学生视角返回专门 VO，剔除 `questionSnapshot` / `ruleConfig`；
`listExams` 对非教师强制 `status >= 1`。

> 注：dev 库里两场考试都是 status=1，没有草稿行，所以"看到草稿"这一条没能实跑到；
> 但"无状态过滤"和"快照泄露"两点均已实测。

### 5. 登录无限流、无锁定、无延迟【实测】

连续 10 次错误密码：
```
状态码序列: 401, 401, 401, 401, 401, 401, 401, 401, 401, 401
非 401 次数: 0
```
全部正常返回"用户名或密码错误"，**没有 429、没有锁定、没有递增延迟**。

`AuthService.login`(65-87) 全文无计数器。`POST /api/auth/login` 是 `permitAll`。
配合生产库里口令为 `123456` 的演示账号，爆破/撞库成本几乎为零。

**修法**：Redis 记录失败次数（生产 Redis 已开启），超阈值锁定或加验证码。

### 6. CORS 全开 + Allow-Credentials【实测】

```
OPTIONS /api/exams   Origin: http://evil.example
-> 200
Access-Control-Allow-Origin: http://evil.example     ← 回显任意来源
Access-Control-Allow-Credentials: true
```

`CorsConfig` 用 `addAllowedOriginPattern("*")` + `setAllowCredentials(true)`。

**缓解因素（必须说清楚）**：前端把 JWT 存在 `localStorage`、通过 `Authorization` 头发送，
**不是 Cookie**。异源页面读不到受害者的 localStorage，所以**当前不构成可直接利用的 CSRF/凭证窃取**。

**但仍应修**：这是不该发布的默认值；一旦将来改用 Cookie 鉴权就立刻变成真漏洞。
而且前端与后端同源（nginx 全部反代到 app），这段 CORS **实际是死配置**——建议直接删或改成白名单。

> 更正：我最初推断"preflight 会被 Spring Security 的 401 挡掉（CorsFilter 顺序问题）"，
> **实测证明我推断错了**——preflight 返回 200 且 CORS 头齐全，过滤器顺序没有问题。

### 7. Docker HEALTHCHECK 永远失败【读码】

`Dockerfile:44`
```dockerfile
HEALTHCHECK CMD curl -fsS http://localhost:8080/api/auth/me || exit 1
```
`/api/auth/me`（`AuthController:42`）需要鉴权（`@AuthenticationPrincipal`），
`SecurityConfig` 只放行了 login/register/refresh → 无 token 访问返回 **401** →
`curl -f` 遇 4xx 退出码 22 → **HEALTHCHECK 永远失败，容器永远 unhealthy**。

`nginx/exam.conf` 的 `location /health` 同样 `proxy_pass .../api/auth/me` → 永远 401，
这个健康检查端点没有任何意义。

compose 不会因此挂掉（nginx 的 `depends_on: app` 没写 `condition`），
但 `docker ps` 会一直显示 unhealthy；**上 K8s / ECS / Swarm 会被反复重启**。

**修法**：加 `spring-boot-starter-actuator`，放行 `/actuator/health`，两处都指过去。

### 8. JWT 密钥在生产是"失败开放"【读码】

- `JwtUtil` 构造器有硬编码兜底默认值
- `application.yml` 里有明文种子密钥
- **`application-prod.yml` 没有引用 `${JWT_SECRET}`**

环境变量**确实生效**（Spring Boot relaxed binding 把 `JWT_SECRET` 映射到 `jwt.secret`，
优先级高于 yml），所以走 docker-compose 部署是对的。

**但漏配时应用会用一个公开已知的密钥正常启动**——任何人可据此伪造管理员 token。
这与我刚给 `DB_PASSWORD` 做的"缺了就启动失败"（fail-closed）不一致。

**修法**：`application-prod.yml` 加 `jwt.secret: ${JWT_SECRET}`（不给默认值）。

## 工程性 / 非安全

### 9. WebSocket 每连接一个线程 + 每秒两次 Redis 往返【读码】
`startCountdownTask` 里 `Executors.newSingleThreadScheduledExecutor()` **每个会话创建一个线程**，
每秒执行一次，且做 **GET 再 getExpire 两次** Redis 往返（只取 TTL 就够了）。
1000 人同时考试 = 1000 个线程 + 每秒 2000 次 Redis 请求。
这是"高并发在线考试系统"这个招牌下**最弱的一环**。
**修法**：全局共享调度器 + 只取 TTL（或 pipeline 批量取）。

### 10. 缺 `.dockerignore`【读码】
构建上下文会把 `target/`（构建产物）和 `data/`（**含 BCrypt 哈希与考试记录的 H2 文件**）
一起发给 Docker daemon。Dockerfile 只 `COPY pom.xml` 和 `COPY src`，所以不会进镜像，
但上下文臃肿、且本地敏感数据被传给 daemon 并进入构建缓存。

### 11. 测试覆盖盲区【读码】
90 个测试全绿，但 **Redis 幂等切面 / RabbitMQ 异步判分 / WebSocket 鉴权 三条路径零集成测试**
（dev 与 test 档都把这两个中间件关掉了）。
上面发现 2 和 Redis 幂等路径就是这么漏过去的。

### 12. 整个 Spring Boot 3 重写从未提交【实测】
`git status` 显示 `src/main/java/com/exam/`、`sql/init.sql`、`nginx/`、`static/`、
`db/migration/` 等**全部处于未跟踪状态**，另有 46 个 `com.caikailang` 旧包文件处于已删除未提交。
**整个 JDK17 + Spring Boot 3 重写只存在于工作区，没有任何回滚点**——
一次 `git clean -fd` 或误操作 `git checkout .` 就会全部丢失。建议尽快提交一次。

## 查过、确认没问题的（避免只报坏消息）

- **无 SQL 注入**：`src/main/resources/mapper/` 下所有 XML 中 **没有任何 `${}` 拼接**
- **注册不可提权**：`RegisterForm` 没有 role 字段，`AuthService.register` 硬编码 `user.setRole(2)` 并注明"强制学生角色"
- **QuestionController 9 个端点全部带 `@PreAuthorize("hasAnyRole('ADMIN','TEACHER')")`**
- **nginx 配置合法**：无 BOM（首字节 `23 20 4e 67 69 6e`）、49 行全 LF、注释未吞掉后续指令
  （我最初怀疑它被写坏了，是用 PowerShell 读出来乱码导致误判，已排除）
- **JWT 实现规范**：用 `Keys.hmacShaKeyFor` + `verifyWith`（非已废弃 API），算法固定，无 alg=none 风险
- **密码存储**：BCrypt，且有 `DemoDataPasswordTest` 校验种子哈希确实对应口令
- **重复交卷防护写得对**：归属校验 + `status==ONGOING` 校验 + `compareAndSetSubmit` CAS 三层
- **归属越权防护**：`submitExam` / `getResult` 都校验 `record.getUserId().equals(userId)`
